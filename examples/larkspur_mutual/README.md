# Larkspur Mutual: the pipeline run on a made-up company

**Larkspur Mutual Insurance Company is fictional.** The people, numbers, systems and data
in this directory were invented for this example. None of it is from, or about, a real
insurer.

This is the Model Project Constructor run end to end on a hypothetical property and
casualty claims problem: *flag, at first notice of loss, the physical-damage claims that
will end as total losses, so they are decided in two days instead of five.* It needs no
API key and no repository host, and it makes no network call.

## Run it

From the repository root (needs `uv sync --extra agents --extra ui --extra dev`):

```bash
uv run python examples/larkspur_mutual/run_example.py
```

It takes about two seconds and writes everything to `out/` (not tracked by git):

| Step | What runs | Output |
|---|---|---|
| 1. Interview | The real intake web UI, driven over HTTP, answering from `intake_fixture.yaml` | `out/intake_report.json` |
| 2. Data | A generated 40,000-claim SQLite database (`make_synthetic_db.py`) | `out/larkspur_claims.db` |
| 3. Pipeline | The shipped orchestrator, `DataAgent` and `WebsiteAgent`, onto an in-memory repository | `out/project/` (55 files plus `EXAMPLE_NOTICE.md`), `out/checkpoints/` |

To play the stakeholder yourself instead, run `uv run python examples/larkspur_mutual/serve_intake.py`,
open http://127.0.0.1:8000/ and type the `qa_pairs` answers from `intake_fixture.yaml`.

The step 3 output ends:

```
  status:  COMPLETE
  project: https://fake.host.test/larkspur-claims-analytics/total-loss-fnol-pilot
  data:    14 quality checks run, 11 passed, 3 failed

The scaffolded project (55 files, plus EXAMPLE_NOTICE.md) is in .../out/project
Checkpoints: .../out/checkpoints/larkspur_tl_fnol_keyless
```

Nothing in `tests/` or CI runs this example, so the figures in this file are observations,
not guarantees. `run_example.py` does stop if the database no longer matches the counts the
datasheets quote.

## What is real and what is a stand-in

The point of a keyless run is that the machinery is real and the model is not.

| | Real (the shipped code) | Stand-in |
|---|---|---|
| Interview | The FastAPI app, its sessions, its review step, the `IntakeReport` validation | The questions, the draft and the governance block (`intake_fixture.yaml`), replayed by the shipped `FixtureLLMClient`; the stakeholder's answers |
| Data | `DataAgent`, its graph, the quality checks and the baseline query executed against the database | The SQL, the expectation text, the datasheets and the summary wording (`scripted_data_llm.py`); the database itself is generated |
| Website | `WebsiteAgent`, every template, the governance files | The repository (in memory, so nothing is created anywhere) |

**The stand-in text was drafted with an AI coding assistant working with the operator.** It was
not generated by the pipeline's own model at run time, and it is not a transcript of one.
So this shows what the tool does with a well-formed interview and a database. It does not show
what Claude would ask, what SQL it would write, or whether it would find the data problems.

The generated project says so itself: its business problem calls Larkspur "a fictitious insurer",
the datasheets say SYNTHETIC, and `run_example.py` adds an `EXAMPLE_NOTICE.md` to it.

### What the three failing checks do and do not show

The stakeholder's three data worries (a blank `drivable` flag, a vehicle value of 0, decision
times before first notice) were planted by `make_synthetic_db.py`, and the author wrote the
three checks that fail knowing them. So the failures show that the agent executes checks and
reports their results; they do not show that it discovers problems. The worries never reach the
data stage in any case: the adapter that builds the data request hard-codes an empty
`data_quality_concerns` (see finding 3). Some passing checks are true by construction
(`claim_ids_unique`, for one: it is the primary key).

The database is a scaled-down extract: 40,000 claims over 34 months, about 14,100 a year,
against the 180,000 a year in the stakeholder's value case. The datasheets say so.

## What the tool got wrong on this run

Found while building and reviewing the example; none was fixed here. (Finding 4 was fixed afterwards,
in Session 288, finding 7 and the install and formatting parts of finding 8 in Session 290; the
others were not.) Provenance: **ran** = I ran it while building this example;
**read** = I read the code and did not run it; **review** = an independent reviewer ran or read it, a
second reviewer could not refute it, and I have not re-run it.

**The interview and the pipeline**

1. **No flag of `scripts/run_pipeline.py` takes an `IntakeReport` (ran: `--help` lists 12 flags).**
   The routes that exist are the programmatic `run_pipeline` call, which this example uses; placing
   an `IntakeReport` envelope in a checkpoint directory and using `--resume` (read); and `--llm both`,
   which has a live model ask the questions while a YAML file supplies the answers (read).
2. **The terminal CLI cannot interview (ran: `model-intake-agent --anthropic` exits 2, "not shipped in
   Phase 3A").** The web UI is the only live interview. It keeps the report in its session database
   and serves it at `/sessions/{id}/report.json`; it does not export it as a file, so
   `drive_interview.py` fetches and saves it (ran). Importing the UI package also opens
   `./intake_sessions.db` in the working directory as a side effect (read: `ui/intake/app.py`).
3. **What the interview learns about the data is not passed to the data stage (read:
   `orchestrator/adapters.py`).** `intake_report_to_data_request` sets `data_quality_concerns=[]`, and
   the request's `time_range` is the fixed default "last 5 calendar years of historical records",
   where this database holds 34 months.

**The data stage**

4. **`ReadOnlyDB` was not read-only; fixed in Session 288 (ran, on a scratch copy, before the fix).**
   On SQLite, `DROP TABLE` and `CREATE TABLE` through `ReadOnlyDB.execute` persisted; `DELETE` and
   `UPDATE` ran and were rolled back only because nothing commits. `validate_sql` runs on the primary
   queries only, so the quality-check and baseline SQL were executed unvalidated. Now `execute`
   refuses anything but one `SELECT`, `WITH` or `VALUES` statement before the database is touched,
   and `connect` opens the connection read-only on SQLite, PostgreSQL, MySQL and MariaDB (any other
   dialect: a WARNING, and only the statement gate). This example still runs to `COMPLETE` with 14
   quality checks, 11 passed and 3 failed, none refused. Connect an account that cannot write
   anyway: the gate over-refuses on purpose, and it cannot stop an expensive `SELECT` or a
   side-effecting function it does not list.
5. **A failed quality check says nothing about how many rows fail (ran).** It carries `row_count: 0`
   and `sample_rows: []`. The database holds 173, 1,226 and 9 offending rows; the report cannot say so.
6. **The baseline is a bare number (ran for the value; review for the rest).** The snapshot value is
   4.878912037005648 with no caveats and no window start or end, the generated plan prints
   "Measurement window: (not recorded)", and the baseline SQL is saved only inside `data_report.json`,
   not under `queries/`.

**The scaffold it wrote**

7. **The generated project failed its own tests; fixed in Session 290 (ran, before the fix).** All 8
   failed: four imported a module literally named `<project_slug>` (an unrendered placeholder in the
   website agent's templates), four put `pass` inside `pytest.raises`. Now each test imports the
   project's real package and each stub test calls its stubs inside `pytest.raises(NotImplementedError)`,
   so a new scaffold is green and a stub that is implemented turns its test red, which is the prompt to
   replace it. Regenerated by `run_example.py`, `out/project/` gives 8 passed on a clean `PATH` after
   `uv sync --extra dev`, and `ruff check` and `ruff format --check` are clean under ruff 0.17.3 and
   under 0.5.0, the version its pre-commit hook pins. `tests/agents/website/test_scaffold_runs.py` now
   runs a scaffold's own tests and ruff for four variants of the pipeline's input (not this example's
   data), so the next such defect fails the suite.
8. **Its tooling: the install and formatting parts were fixed in Session 290; two parts are open
   (review; ran for the fixed parts).** Fixed: a bare `uv sync` did not install the `dev` extra that holds
   `pytest` and `ruff`, so its CI would have failed before it reached the tests (its README,
   `.gitlab-ci.yml` and GitHub workflow now run `uv sync --extra dev`); and its pre-commit `ruff-format`
   hook would have reformatted four test files (it now changes nothing). Still open: its `governance` CI
   job only parses the registry as JSON and, on GitLab, runs in a stage after `test`, so a failing test
   job hides it; and notebooks 02 to 05 cannot render because no Jupyter is declared.
9. **Its prose is partly stale or thin (review).** The README and `data/README.md` still say datasheets
   and governance files arrive "in Phase 4B" although both are present, and a notebook points at a
   `src/fairness/` that does not exist; the target definition and the 12 candidate features appear in
   no human-readable document, only in the JSON and the SQL; the stakeholder's request for a review of
   who gets the fast track is reduced to booleans in the governance files; and at risk tier 3 no
   `regulatory_mapping.md` is emitted, so the NAIC mapping is visible only in the checkpoint.

**Live hosts (not exercised here)**

10. **`--host` and `MPC_HOST` can disagree about which token to send (read).** In
    `scripts/run_pipeline.py` the token variable follows `MPC_HOST` (default `gitlab`) while the adapter
    and URL follow `--host`, so `--host github --live` with `GITLAB_TOKEN` set sends that token to
    `api.github.com`.
11. **The GitHub live path probably fails (read, inferred).** The adapter creates the repository with no
    `auto_init` and then reads `git/ref/heads/<branch>`, which an empty repository does not have. It has
    never been run against a real host.

## Not covered

A live model (Claude's own questions, SQL and datasheets), a real repository host, the revision loop in
the review step, an intake that ends `DRAFT_INCOMPLETE`, a stage that fails or retries, resuming from a
checkpoint, the standalone `model-data-agent` command, `--inventory-from-intake`, a database that is not
SQLite, and any modeling: the generated project's `src/` is stubs by design, and no model is trained
here. The data is also far easier to separate than a real book would be (vehicle age alone has an AUC of
about 0.86, because the generator decides a total loss from repair cost against value), which the
datasheet says.
